# MVP-004 — شاخص‌های کیفیت و موفقیت زمان‌بندی هوشمند

**وضعیت:** نهایی برای MVP  
**دامنه:** سنجش کیفیت هر برنامه و ارزیابی عملکرد قابلیت در دوره آزمایشی  
**پیش‌نیازها:** [MVP-001](./MVP_001_scheduling_hard_constraints.md)، [MVP-002](./MVP_002_scheduling_soft_constraints.md)، [MVP-003](./MVP_003_scheduling_time_groups.md)  
**مالک تصمیم:** محصول آموزشی / سوپروایزر

---

## ۱. هدف

این سند مشخص می‌کند کیفیت یک Scheduling Plan چگونه سنجیده شود و بعد از استفاده واقعی چگونه بفهمیم قابلیت زمان‌بندی هوشمند بخشی از کار سوپروایزر را کاهش داده است.

شاخص‌ها به دو گروه تقسیم می‌شوند:

1. **شاخص‌های کیفیت برنامه:** هنگام تولید و پیش از انتشار محاسبه می‌شوند؛
2. **شاخص‌های عملکرد محصول:** پس از بررسی و تصمیم سوپروایزر اندازه‌گیری می‌شوند.

هیچ شاخص ترجیحی به‌تنهایی انتشار را مسدود نمی‌کند. تنها وجود Hard Constraint نقض‌شده مانع انتشار است.

---

## ۲. جمعیت مبنا

برای جلوگیری از آمار گمراه‌کننده، تمام شاخص‌ها باید در یک محدوده مشخص محاسبه شوند:

- یک `instituteId`؛
- یک `termId`؛
- یک شعبه یا محدوده همه شعبه‌های انتخاب‌شده؛
- Courseهای قرارگرفته در نیاز همان اجرا؛
- دانش‌آموزان فعال دارای `currentAllowedCourseId` متناظر؛
- استادان فعال و واجد شرایط همان Courseها.

دانش‌آموز تکراری در شاخص پوشش هر Course فقط یک‌بار شمرده می‌شود.

---

## ۳. شاخص‌های کیفیت برنامه

### QM-001 — تعداد تخلف‌های قطعی

```text
hardViolationCount = count(all hard-constraint violations)
```

| وضعیت          |      مقدار |
| -------------- | ---------: |
| قابل انتشار    |          0 |
| غیرقابل انتشار | بیشتر از 0 |

این تنها شاخص مسدودکننده انتشار است و باید بلافاصله پیش از انتشار دوباره محاسبه شود.

### QM-002 — نرخ تأمین نیاز کلاس‌ها

```text
demandFulfillmentRate = scheduledRequestedClasses / requestedClasses × 100
```

- صورت فقط کلاس‌های پیشنهادی کامل و معتبر را شامل می‌شود.
- نیاز بدون راه‌حل در مخرج باقی می‌ماند.
- تعداد حل‌نشده باید به تفکیک Course همراه با Reason Code نمایش داده شود.

| وضعیت اولیه   |                 نرخ |
| ------------- | ------------------: |
| مطلوب         |                100٪ |
| نیازمند بررسی | 90٪ تا کمتر از 100٪ |
| ضعیف          |         کمتر از 90٪ |

### QM-003 — کامل بودن داده زمانی دانش‌آموزان

```text
studentScheduleCompleteness = studentsWithCompleteSchedule / eligibleActiveStudents × 100
```

| وضعیت اولیه |                نرخ |
| ----------- | -----------------: |
| قابل اتکا   |       90٪ یا بیشتر |
| متوسط       | 80٪ تا کمتر از 90٪ |
| کم‌اتکا     |        کمتر از 80٪ |

این شاخص امتیاز برنامه را تغییر نمی‌دهد، اما میزان قابل اعتماد بودن محاسبه پوشش را نشان می‌دهد.

### QM-004 — پوشش یکتای دانش‌آموزان

```text
studentAccessCoverage = coveredStudentsWithKnownSchedule / studentsWithKnownSchedule × 100
```

یک دانش‌آموز زمانی پوشش‌داده‌شده است که حداقل یک کلاس از سطح مجازش وجود داشته باشد که بتواند در تمام جلسات آن شرکت کند.

| وضعیت اولیه   |                نرخ |
| ------------- | -----------------: |
| عالی          |       90٪ یا بیشتر |
| قابل قبول     | 80٪ تا کمتر از 90٪ |
| نیازمند بررسی | 65٪ تا کمتر از 80٪ |
| ضعیف          |        کمتر از 65٪ |

### QM-005 — کمترین پوشش یک سطح

```text
minimumCourseCoverage = min(courseCoverage for every requested course)
```

این شاخص مانع پنهان‌شدن وضعیت یک سطح کم‌جمعیت در میانگین کل می‌شود.

| وضعیت اولیه   |                نرخ |
| ------------- | -----------------: |
| مطلوب         |       80٪ یا بیشتر |
| نیازمند بررسی | 65٪ تا کمتر از 80٪ |
| ضعیف          |        کمتر از 65٪ |

### QM-006 — تحقق تنوع زمانی

```text
timePatternFulfillment = SC-002 normalizedScore × 100
```

این شاخص میزان تحقق الگوی فرد/زوج و صبح/عصر تعریف‌شده در MVP-002 و MVP-003 را نشان می‌دهد.

| وضعیت اولیه   |                نرخ |
| ------------- | -----------------: |
| مطلوب         |       90٪ یا بیشتر |
| قابل قبول     | 70٪ تا کمتر از 90٪ |
| نیازمند بررسی |        کمتر از 70٪ |

### QM-007 — عدالت بار استادان

برای هر استاد واجد شرایط ابتدا نسبت بار محاسبه می‌شود:

```text
teacherLoadRatio = assignedTeachingMinutes / availableTeachingMinutes
```

سپس شاخص عدالت محاسبه می‌شود:

```text
teacherLoadFairness = clamp(1 - (maxLoadRatio - minLoadRatio), 0, 1) × 100
```

- کلاس‌های واقعی همان ترم نیز در زمان تخصیص‌یافته حساب می‌شوند.
- استادانی که برای هیچ نیاز اجرا واجد شرایط نیستند از محاسبه حذف می‌شوند.
- اگر کمتر از دو استاد قابل مقایسه باشند، شاخص `NOT_APPLICABLE` است.

| وضعیت اولیه |                نرخ |
| ----------- | -----------------: |
| متعادل      |       80٪ یا بیشتر |
| قابل قبول   | 60٪ تا کمتر از 80٪ |
| نامتعادل    |        کمتر از 60٪ |

### QM-008 — رضایت ترجیح زمانی دانش‌آموزان

```text
studentPreferenceSatisfaction = studentsWithPreferredOption / coveredStudentsWithPreferences × 100
```

اگر هیچ دانش‌آموز پوشش‌داده‌شده‌ای ترجیح زمانی ثبت نکرده باشد، مقدار `NOT_APPLICABLE` است.

### QM-009 — شاخص کیفیت ترکیبی

دو مقدار باید کنار هم ذخیره و نمایش داده شوند:

```text
earnedWeightedPoints = sum(normalizedScore × configuredWeight)
applicableWeightedPoints = sum(weight of applicable metrics)
qualityIndex = earnedWeightedPoints / applicableWeightedPoints × 100
```

- `earnedWeightedPoints` امتیاز خام مطابق MVP-002 است و معیار `NOT_APPLICABLE` برای آن امتیاز ایجاد نمی‌کند.
- `qualityIndex` برای گزارش و مقایسه منصفانه برنامه‌ها میان اجراهای مختلف استفاده می‌شود که بعضی معیارهایشان قابل محاسبه نیست.
- UI باید هر دو مقدار را به‌صورت شفاف نمایش دهد؛ برای مثال `78 از 95 — شاخص کیفیت 82٪`.
- برنامه‌های یک اجرای واحد، مجموعه معیارهای قابل محاسبه یکسانی دارند و مطابق MVP-002 با `earnedWeightedPoints` رتبه‌بندی می‌شوند.
- قانون برتری پوشش ۵ واحد درصدی پیش از هر نوع رتبه‌بندی اعمال می‌شود.

| سطح کیفیت     |      Quality Index |
| ------------- | -----------------: |
| عالی          |       90٪ یا بیشتر |
| خوب           | 80٪ تا کمتر از 90٪ |
| نیازمند بررسی | 65٪ تا کمتر از 80٪ |
| ضعیف          |        کمتر از 65٪ |

## ۴. شاخص‌های عملکرد محصول

این شاخص‌ها کیفیت الگوریتم را در استفاده واقعی می‌سنجند و برای هر آموزشگاه و ترم گزارش می‌شوند.

### PM-001 — نرخ پذیرش پیشنهاد اول بدون ویرایش

```text
firstProposalAcceptanceRate = plansPublishedWithoutManualEdit / reviewedPlans × 100
```

افزایش این عدد نشانه نزدیک‌تر شدن پیشنهاد موتور به تصمیم سوپروایزر است.

### PM-002 — نرخ برنامه‌های نیازمند ویرایش

```text
manualAdjustmentRate = plansWithAtLeastOneManualEdit / reviewedPlans × 100
```

تعداد و نوع ویرایش‌ها نیز باید تفکیک شود: استاد، روز، ساعت، اتاق یا حذف/افزودن کلاس.

### PM-003 — نرخ کلاس‌های تغییرکرده

```text
changedSuggestionRate = manuallyChangedSuggestedClasses / allSuggestedClasses × 100
```

این شاخص از PM-002 دقیق‌تر است؛ ممکن است یک برنامه بزرگ فقط یک تغییر کوچک داشته باشد.

### PM-004 — نرخ انتشار موفق

```text
publicationRate = publishedPlans / reviewedPlans × 100
```

وضعیت‌های رهاشده، ردشده و بدون راه‌حل باید جداگانه گزارش شوند.

### PM-005 — کاهش زمان کار سوپروایزر

```text
reviewDuration = publishedAt - firstReviewStartedAt
```

برای سنجش کاهش واقعی کار، در دوره آزمایشی باید زمان تقریبی برنامه‌ریزی دستی یک ترم نیز ثبت شود. هدف کمی نهایی پس از ایجاد baseline اولین دوره تعیین می‌شود.

### PM-006 — دلایل رد یا تغییر پیشنهاد

هنگام رد کامل برنامه یا تغییر یک پیشنهاد، ثبت دلیل در MVP اختیاری اما توصیه‌شده است. Reason Codeهای اولیه:

- `STUDENT_ACCESS`
- `TEACHER_PREFERENCE`
- `TIME_PATTERN`
- `CLASSROOM`
- `WORKLOAD`
- `OPERATIONAL_REASON`
- `OTHER`

## ۵. Snapshot و قابلیت ممیزی

هر Scheduling Plan باید داده‌های زیر را به‌صورت Snapshot نگهداری کند:

- تعداد دانش‌آموزان مبنا و میزان کامل بودن داده؛
- مقدار تمام QMها؛
- وزن‌های استفاده‌شده؛
- تنظیمات گروه‌های زمانی؛
- تعداد نیازهای برنامه‌ریزی‌شده و حل‌نشده؛
- نسخه فرمول امتیازدهی؛
- زمان تولید و زمان آخرین محاسبه؛
- تعداد و نوع تغییرات دستی.

تغییر داده‌های زنده نباید شاخص تاریخی برنامه منتشرشده را بازنویسی کند.

---

## ۶. رفتار داده‌های خاص

- اگر هیچ دانش‌آموزی برای Course وجود نداشته باشد، پوشش آن Course برابر `NOT_APPLICABLE` است، نه صفر.
- اگر دانش‌آموز وجود دارد اما هیچ برنامه زمانی کامل نیست، پوشش `NOT_APPLICABLE` و کامل‌بودن داده صفر درصد است.
- اگر هیچ کلاس درخواستی وجود ندارد، اجرای زمان‌بندی باید در مرحله preflight متوقف شود و Plan امتیازدار نسازد.
- اگر تنها یک استاد واجد شرایط وجود دارد، عدالت بار `NOT_APPLICABLE` است.
- مقدار `NOT_APPLICABLE` نباید در UI به شکل صفر نمایش داده شود.
- درصدها با دقت دو رقم اعشار ذخیره و برای نمایش به عدد صحیح گرد شوند.

## ۷. هدف دوره آزمایشی

برای اولین ترم پایلوت، موفقیت قابلیت با این شرایط ارزیابی می‌شود:

- هیچ برنامه منتشرشده‌ای Hard Constraint نقض‌شده نداشته باشد؛
- داده زمانی حداقل 80٪ دانش‌آموزان هدف کامل باشد؛
- میانگین پوشش شناخته‌شده حداقل 80٪ باشد؛
- تمام نیازهای حل‌نشده Reason Code داشته باشند؛
- زمان بررسی و میزان ویرایش برای ساخت baseline ثبت شود.

برای PM-001 تا PM-005 قبل از اولین پایلوت هدف عددی قطعی تعیین نمی‌شود؛ مقدار اولین ترم baseline است و هدف بهبود ترم بعد براساس داده واقعی تعیین خواهد شد.
