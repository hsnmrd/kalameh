# MVP-009 — مدل اجرای زمان‌بندی و پیش‌نویس برنامه

**وضعیت:** پیاده‌سازی‌شده  
**دامنه:** ذخیره اجرای موتور، برنامه‌های جایگزین، کلاس‌های پیشنهادی و خروجی‌های حل‌نشده  
**پیش‌نیازها:** [MVP-001](./MVP_001_scheduling_hard_constraints.md)، [MVP-004](./MVP_004_scheduling_quality_metrics.md) و [MVP-008](./MVP_008_class_requirements.md)

---

## ۱. جداسازی از کلاس واقعی

زمان‌بندی خودکار مستقیماً `Class` ایجاد نمی‌کند. هر درخواست ابتدا یک `SchedulingRun` می‌سازد و خروجی آن در یک یا چند `SchedulingPlan` ذخیره می‌شود. هر Plan شامل `SchedulingProposal`هایی است که تا زمان انتشار صرفاً پیش‌نویس هستند.

این جداسازی امکان مقایسه گزینه‌ها، ویرایش، قفل‌کردن، بازتولید و بررسی نهایی Hard Constraintها را بدون تغییر کلاس‌های عملیاتی فراهم می‌کند.

## ۲. اجرای زمان‌بندی

وضعیت‌های `SchedulingRun`:

- `QUEUED`؛
- `PREFLIGHT_FAILED`؛
- `GENERATING`؛
- `COMPLETED`؛
- `FAILED`؛
- `CANCELLED`.

هر اجرا آموزشگاه، ترم، شعبه اختیاری، درخواست‌کننده و Snapshot ورودی/تنظیمات را نگه می‌دارد. `sourceRunId` زنجیره بازتولید را بدون بازنویسی اجرای قبلی حفظ می‌کند. گزارش preflight و اطلاعات خطا نیز روی Run ذخیره می‌شوند.

اگر preflight به دلیل نبود Requirement یا داده مسدودکننده شکست بخورد، Run با `PREFLIGHT_FAILED` باقی می‌ماند و Plan امتیازدار ساخته نمی‌شود.

## ۳. برنامه‌های پیشنهادی

وضعیت‌های Plan:

- `DRAFT`؛
- `SELECTED`؛
- `PUBLISHED`؛
- `REJECTED`؛
- `SUPERSEDED`.

هر Plan یک رتبه یکتا در Run دارد و می‌تواند به‌عنوان پیشنهاد اول علامت‌گذاری شود. داده‌های زیر به‌صورت تاریخی ذخیره می‌شوند:

- امتیاز خام، وزن قابل‌اعمال و Quality Index؛
- درصد پوشش کل و کمترین پوشش Course؛
- breakdown امتیاز و تمام شاخص‌ها؛
- Snapshot وزن‌ها، گروه‌های زمانی و کامل‌بودن داده؛
- هشدارها و نسخه فرمول؛
- زمان تولید و آخرین امتیازدهی؛
- تعداد و زمان ویرایش/بررسی/انتخاب/رد/انتشار.

تغییر تنظیمات زنده، امتیاز Plan موجود را تغییر نمی‌دهد.

## ۴. کلاس و جلسات پیشنهادی

`SchedulingProposal` موارد زیر را نگه می‌دارد:

- Requirement، Course و شعبه؛
- استاد، شناسه Qualification استفاده‌شده و زمان بررسی صلاحیت؛
- اتاق اختیاری و شیوه حضوری/آنلاین؛
- عنوان، ظرفیت، الگوی روزها، ساعت شروع/پایان و گروه زمانی؛
- وضعیت قفل، کاربر قفل‌کننده و زمان قفل؛
- وضعیت و تعداد ویرایش دستی و هشدارها؛
- ارتباط اختیاری با Class ساخته‌شده پس از انتشار.

تاریخ جلسات در `SchedulingProposalSession` به‌صورت رکوردهای مستقل نگه‌داری می‌شوند. این ساختار بررسی تداخل روی تاریخ واقعی و قرارداد بازه نیمه‌باز را ممکن می‌کند و از تکرار یک جلسه با تاریخ و ساعت شروع یکسان جلوگیری می‌کند.

## ۵. نیازهای حل‌نشده

`SchedulingUnresolvedRequirement` تعداد کلاس‌های تولیدنشده هر Requirement، Reason Code و جزئیات قابل توضیح را ذخیره می‌کند. موتور نباید برای کاهش ظاهری این تعداد، Proposal ناقص ایجاد کند.

## ۶. روابط و حذف

- حذف Run، Planهای وابسته و تمام Proposalها، Sessionها و موارد حل‌نشده آن را حذف می‌کند.
- حذف Plan نیز تمام محتوای پیش‌نویس آن را Cascade می‌کند.
- حذف شعبه یا اتاق از داده زنده، مرجع اختیاری Proposal را null می‌کند ولی Snapshot Plan باقی می‌ماند.
- حذف Requirement پس از تولید، شناسه زنده را null می‌کند و Snapshot ورودی اجرای تاریخی حفظ می‌شود.
- استاد و Course استفاده‌شده در Proposal تا تعیین تکلیف برنامه قابل حذف فیزیکی نیستند.
- حذف کل آموزشگاه تمام داده زمان‌بندی آن را حذف می‌کند.

تمام عملیات API باید هم‌مالک بودن Institute، Run، Plan، Proposal، Session و مراجع زنده را کنترل کنند؛ UUID معتبر به‌تنهایی کافی نیست.

## ۷. انتشار

- فقط یک Plan معتبر و انتخاب‌شده قابل انتشار است.
- پیش از انتشار، تمام Hard Constraintها با داده زنده دوباره بررسی می‌شوند.
- انتشار باید در یک transaction تمام Classها را ایجاد و `publishedClassId` هر Proposal را ثبت کند.
- وجود تخلف قطعی انتشار کل Plan را متوقف می‌کند.
- Plan منتشرشده و Snapshotهای آن نباید ویرایش شوند.

این رفتار در لایه سرویس انتشار پیاده‌سازی خواهد شد.
