# MVP-008 — مدل نیاز کلاس‌های ترم

**وضعیت:** پیاده‌سازی‌شده  
**دامنه:** مدل داده ورودی کلاس‌های موردنیاز برای زمان‌بندی خودکار  
**وابسته به:** HC-003 و HC-013 در [MVP-001](./MVP_001_scheduling_hard_constraints.md)

---

## ۱. هدف

`ClassRequirement` نیاز آموزشی یک Course را در یک Term ثبت می‌کند. این رکورد Class واقعی یا پیش‌نویس زمان‌بندی نیست؛ ورودی موتور است و مشخص می‌کند چند کلاس با چه ظرفیت، مدت جلسه و آهنگ برگزاری باید ساخته شود.

فلو دستی فعلی ساخت Class بدون تغییر باقی می‌ماند.

## ۲. قرارداد مدل

هر نیاز شامل داده‌های زیر است:

- `instituteId`: آموزشگاه مالک؛
- `termId`: ترم هدف؛
- `courseId`: سطح یا دوره آموزشی؛
- `branchId`: شعبه هدف یا مقدار خالی برای نیاز سراسری آموزشگاه؛
- `requiredClassCount`: تعداد کلاس موردنیاز؛
- `capacity`: ظرفیت هر کلاس؛
- `sessionDurationMinutes`: مدت هر جلسه به دقیقه؛
- `sessionsPerWeek`: تعداد جلسات هفتگی؛
- `totalSessions`: تعداد کل جلسات؛
- `deliveryMode`: یکی از `IN_PERSON` یا `ONLINE`؛
- `isActive`: امکان خارج‌کردن نیاز از اجرای زمان‌بندی بدون حذف سابقه.

## ۳. قواعد دامنه

- Institute، Term، Course و Branch باید متعلق به یک آموزشگاه باشند.
- `requiredClassCount`، `capacity` و `sessionDurationMinutes` باید اعداد صحیح مثبت باشند.
- دقیقاً یکی از `sessionsPerWeek` یا `totalSessions` باید مقدار مثبت داشته باشد.
- نیاز حضوری هنگام زمان‌بندی به اتاق معتبر با ظرفیت کافی احتیاج دارد.
- نیاز آنلاین نباید اتاق فیزیکی اشغال کند.
- نیاز غیرفعال وارد تولید کاندید نمی‌شود.
- چند رکورد برای یک Course مجاز است؛ برای مثال وقتی ظرفیت، شعبه، شیوه برگزاری یا آهنگ جلسات متفاوت باشد.
- حذف Institute، Term، Course یا Branch، نیاز وابسته را با Cascade حذف می‌کند.

اعتبارسنجی مقادیر مثبت، cadence انحصاری و هم‌مالک بودن مراجع در Schema و API مدیریت نیازها اعمال خواهد شد.

## ۴. رفتار زمان‌بندی

- موتور حداکثر به تعداد `requiredClassCount` پیشنهاد تولید می‌کند.
- اگر تولید تمام تعداد ممکن نباشد، نیاز حل‌نشده باقی می‌ماند و کلاس ناقص ساخته نمی‌شود.
- `sessionDurationMinutes` باید با اختلاف زمان شروع و پایان تمام جلسات پیشنهادی برابر باشد.
- `sessionsPerWeek` یا `totalSessions` مبنای تولید و بررسی `sessionDates` است.
- تغییر نیاز، Classهای واقعی قبلی را ویرایش یا حذف نمی‌کند.

## ۵. انتقال داده موجود

از Classهای موجود هیچ Requirementی استنتاج نمی‌شود؛ زیرا ممکن است کلاس‌های قبلی استثنایی یا دستی باشند. Migration فقط مدل جدید را ایجاد می‌کند و داده‌های فعلی بدون تغییر باقی می‌مانند.

## ۶. ادامه پیاده‌سازی

- قراردادهای مشترک Zod برای ایجاد، ویرایش و فیلتر نیازها؛
- API tenant-safe مدیریت ClassRequirement در MVP-014؛
- فرم مدیریت نیازهای هر ترم؛
- مصرف Requirementها توسط موتور تولید و گیت انتشار.
