# MVP-010 — جزئیات و توضیح‌پذیری پیشنهاد هر کلاس

**وضعیت:** پیاده‌سازی‌شده  
**دامنه:** ذخیره جزئیات، امتیاز، دلایل انتخاب و هشدارهای هر کلاس پیشنهادی  
**پیش‌نیاز:** [MVP-009](./MVP_009_scheduling_runs_and_plans.md)

---

## ۱. مرز این تسک

هر `SchedulingProposal` یک کلاس پیشنهادی داخل یک `SchedulingPlan` است و تا زمان انتشار، `Class` واقعی محسوب نمی‌شود. اطلاعات ساختاری استاد، Course، Requirement، شعبه، اتاق، شیوه برگزاری، ظرفیت، روزها، ساعت و تاریخ جلسات در MVP-009 ایجاد شده‌اند.

MVP-010 قرارداد توضیح‌پذیری همان پیشنهاد را تکمیل می‌کند تا سوپروایزر فقط نتیجه نبیند و بتواند علت انتخاب آن را بررسی کند.

## ۲. امتیاز هر پیشنهاد

فیلدهای زیر روی `SchedulingProposal` ذخیره می‌شوند:

- `score`: امتیاز نهایی پیشنهاد در بازه صفر تا صد؛
- `scoreBreakdown`: سهم معیارهای قابل محاسبه در امتیاز؛
- `scoredAt`: زمان آخرین محاسبه امتیاز.

`score` با امتیاز کل `SchedulingPlan` یکسان نیست. معیارهایی مانند توازن بار استادان و تنوع کل برنامه ممکن است فقط در سطح Plan معنا داشته باشند. امتیاز Proposal کیفیت همان تخصیص استاد، زمان و اتاق را نشان می‌دهد.

اگر پیشنهاد تازه به‌صورت دستی تغییر کرده و هنوز دوباره ارزیابی نشده باشد، `score` و `scoredAt` می‌توانند `null` شوند. مقدار خالی نباید به‌عنوان امتیاز صفر نمایش داده شود.

ساختار `scoreBreakdown`:

```json
{
  "criteria": [
    {
      "code": "SC_STUDENT_COVERAGE",
      "rawValue": 0.84,
      "normalizedScore": 0.84,
      "weight": 50,
      "weightedPoints": 42,
      "status": "APPLICABLE"
    }
  ]
}
```

مقادیر عددی برای محاسبه و UI ذخیره می‌شوند؛ عنوان معیار باید با `code` در فرانت‌اند ترجمه شود و متن ترجمه‌شده منبع تصمیم‌گیری نیست.

## ۳. دلایل انتخاب

`selectionReasons` یک آرایه JSON و به‌صورت پیش‌فرض خالی است. هر دلیل باید حداقل شامل `code` باشد و می‌تواند شواهد ساخت‌یافته مرتبط را نیز نگه دارد:

```json
[
  {
    "code": "MAXIMIZES_STUDENT_COVERAGE",
    "evidence": {
      "eligibleStudents": 21,
      "coveredStudents": 18,
      "coveragePercent": 85.71
    }
  },
  {
    "code": "IMPROVES_TIME_DIVERSITY",
    "evidence": {
      "timeGroup": "ODD_MORNING"
    }
  }
]
```

Reason Code به‌جای متن آماده نمایش ذخیره می‌شود تا API و UI بتوانند توضیح فارسی و انگلیسی یکسان و قابل نسخه‌بندی تولید کنند. ترتیب آرایه، ترتیب اهمیت دلایل را نشان می‌دهد.

کدهای اولیه:

- `MAXIMIZES_STUDENT_COVERAGE`؛
- `IMPROVES_TIME_DIVERSITY`؛
- `MATCHES_TEACHER_QUALIFICATION`؛
- `MATCHES_TEACHER_AVAILABILITY`؛
- `BALANCES_TEACHER_LOAD`؛
- `ONLY_FEASIBLE_HARD_CONSTRAINT_OPTION`؛
- `MANUALLY_SELECTED`.

## ۴. هشدارها

فیلد موجود `warnings` جزئیات تمام هشدارهای غیرمسدودکننده پیشنهاد را نگه می‌دارد. `null` یا آرایه خالی یعنی هشدار ثبت‌شده‌ای وجود ندارد.

ساختار هر هشدار:

```json
{
  "code": "LOW_STUDENT_COVERAGE",
  "severity": "WARNING",
  "context": {
    "coveredStudents": 9,
    "eligibleStudents": 20
  }
}
```

Hard Constraint نقض‌شده نباید به هشدار تبدیل شود؛ چنین کاندیدی پیش از ذخیره Proposal حذف می‌شود. هشدارها فقط ضعف‌های قابل قبول، داده ناقص یا Soft Constraintهای برآورده‌نشده را توضیح می‌دهند.

## ۵. ویرایش دستی و محاسبه مجدد

- تغییر استاد، روز، ساعت، اتاق یا Course باید امتیاز قبلی را نامعتبر کند.
- تا پایان ارزیابی مجدد، `score = null` و `scoredAt = null` می‌شوند.
- پس از ارزیابی، `scoreBreakdown`، `selectionReasons`، `warnings` و `scoredAt` باید با هم و در یک transaction جایگزین شوند.
- برای پیشنهاد دستی، دلیل `MANUALLY_SELECTED` ثبت می‌شود؛ توضیح اختیاری اپراتور بعداً می‌تواند در Audit Log نگه‌داری شود.
- Proposal متعلق به Plan منتشرشده قابل تغییر یا امتیازدهی مجدد نیست.

## ۶. قواعد صحت داده

- `score` در صورت وجود باید بین صفر و صد باشد؛ این قاعده در Schema/API مشترک MVP-011 اعتبارسنجی خواهد شد.
- `scoreBreakdown` باید فقط معیارهای نسخه فرمول ذخیره‌شده روی Plan را استفاده کند.
- تمام شناسه‌های Proposal باید متعلق به همان آموزشگاه باشند.
- زمان و جلسات پیشنهادی باید قرارداد بازه نیمه‌باز و Hard Constraintهای MVP-001 را رعایت کنند.
- دلیل و هشدار نباید شامل متن ترجمه‌شده به‌عنوان داده اصلی باشد؛ `code` و `context/evidence` منبع اصلی‌اند.
